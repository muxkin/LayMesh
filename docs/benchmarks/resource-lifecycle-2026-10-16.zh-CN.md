# 文档资源复用、性能配额清理与切页验证

本轮把缓存保留依据改为当前文档及其有效资源引用，移除了原有的容量、页数、项目数和线程配额及其设置入口。原附件、上一版验证包和工作区已有修改均保留。下述性能数据只对应本报告记录的构建、机器和测试条件。

**性能目标尚未全部达到。** Chromium 和 VS Code 的切页响应明显改善，已准备页面的中位数仍超过 100 ms；本机切页测试中 Firefox、WebKit 使用 CPU 绘制，取消低分辨率转场后出现明显性能退化。交付包保留实际显示精度，这项 CPU 转场瓶颈尚未解决。

## 实现范围

- 编译会话以每页的实际求值依赖为根，保留被重放计算引用的子结果；成功版本与最近一次未完成求值分开持有。替换结果、删除页面和关闭会话会清除无引用记录。文字布局、几何、路径和对象构造共享这个生命周期。
- 删除离线编译与放映渲染的三页淘汰、256 MiB 默认额度、缩略图 32 MiB 额度、缓存比例划分、文字与样式 16 MiB 限制、4096 项边界清空、图片源码 32 MiB／128 项、字体描述 128 项及八种转场效果限制。另查到的纯几何缓存 16 MiB／256 项也改为会话持有。
- 移除 VS Code 配额设置和原生 `cache_mb`、`processing_memory_mb`、`image_threads` 设置入口。旧字段兼容读取后忽略；内部兼容方法不再施加容量限制。
- 原生页面编译按系统可用并行度分配图片任务，网页按浏览器提供的并行度安排工作。取消固定 2／4 线程和每 Worker 512 MiB 的估算；删除页面后释放不再使用的编译进程。
- 增量基线保留一份当前场景及当前资源映射，属性补丁应用后替换旧值，恢复时不重播无限增长的补丁历史。存活资源估计不再累加历次传输字节。
- 页面安装、入口画面、结束画面和动画预热分开管理。已准备入口画面可以直接显示；后台先准备邻近页面入口，再准备结束画面和动画缓存，在计算单元之间响应暂停，绘制结束后续做。原有切页按键保护保留。
- CPU 转场按实际显示像素绘制，取消最长边 128 像素缩图。预览与图层额外发现的一亿像素固定门槛也已移除；有效尺寸、数值范围检查和 GPU 完成同步保留，实际分配由 Skia／设备接口决定，语言递归与循环语义未改变。

这不是“所有数字都删除”：时间片让出、输入合并、GPU 在途同步和实际设备尺寸约束具有不同作用。此次也没有修改独立导出路径的栅格尺寸校验。

## 测量方法

机器与软件版本记录在 `resource-lifecycle-2026-10-16/evidence/environment.json`。测试机器为 Ryzen 7 8745H，16 个可用逻辑 CPU，约 20.3 GiB RAM。浏览器采用无头运行；VS Code 在隔离配置中使用真实扩展、原生进程和 Webview，通过 CDP 注入受信任键盘输入。VS Code 测试禁用硬件 GPU，不能将结果直接等同于用户的硬件加速桌面。

切页使用连续 `ArrowDown`／`ArrowRight`，间隔 80 ms，经过作品正常的动画步骤；仅到文档结尾才使用 Home 返回。没有时间轴快进，也没有等待全部页面预热。每个环境、每个版本记录 50 次实际页面切换，并保留保护逻辑丢弃的按键记录。首次遍历与重复遍历分开汇总。

- **开始变化**：按键事件至第一个非零转场进度帧完成 GPU 同步，并经主线程一次 RAF／任务确认。它是可自动复跑的画面提交代理指标，不是显示器扫描输出的物理测量。
- **切页完成**：同一次按键至导航 Promise 完成，包括作品自带的转场和 GPU 完成等待。
- **转场耗时**：运行时的转场执行耗时，作品原有的 650～900 ms 转场不会为了计时缩短。
- **激活请求排队**：发送当前页激活请求至渲染 Worker 开始处理的时间，包括前序工作造成的等待；它不能代表所有 GPU／浏览器绘制等待。按原始调用记录只取该次激活，不叠加与它重叠的旧页绘制和后台准备调用。

这是整组修改的同机对照，不能把总降幅单独归因于某一个容量或数量门槛。CPU 转场还从旧版缩图恢复到完整显示像素，实际绘制工作量随之增加。

对照版本为 navigation-preview-v004。为了统一开始变化的测量端点，仅在独立副本中加入通知及完成同步埋点，原包未修改；对照副本没有改变绘制、缓存或调度策略。原文件和埋点副本的哈希分别保留。初次基线埋点的通知路由错误导致缺失时间戳，整批被完整性断言拒绝；修正后重新开始正式采样，没有剔除缺失值后继续计算。短验证另发现计时包装漏传 Worker 传输参数；修正并确认 VS Code 使用 Worker、无回退后才开始正式统计。这些短验证均不计入结果。

编辑计时从 CodeMirror 源码修改结束至对应版本画面确认，包括 30 ms 输入合并窗口。第 2 页与包含 1,536 条曲线的第 6 页分别测颜色、位置、文字、尺寸，每项 50 次。LCSS 标题改色、全部曲线改色，以及 laydoc 改名、重排、新增、删除也各测 50 次，并记录当前页、目录、整份同步三个终点。浏览器和 VS Code 的目录／整份同步终点不同，表中明确标注。

这两个 LCSS 场景修改共享 `.heading` 和 `.strand` 规则，各页均有匹配对象，因此会更新六页；其中 `.strand` 在第 6 页匹配 1,536 条曲线，在其他页匹配各自的曲线。它们不是“只改一页却无条件重做全部页”的测试。局部 `.lay` 修改和局部依赖回归另行检查未变化页面的复用；laydoc 改名、重排只改变目录，浏览器样本中的页面求值更新列表为空。

laydoc 改名或重排不改变当前页内容，“当前页显示”在这些场景表示确认已有画面仍对应最新源码版本的时间，不意味着重新绘制了一帧。

正式计时串行运行，不与本任务的构建和重负载回归并行。最终包的部分正确性对照并行执行，仅用于通过／失败判定，不作为性能样本。中位数取中间两个值的平均，P95 使用最近秩。原始样本保留，不从尾部剔除慢样本。

## 实测结果

连续切页中，Chromium 的开始响应中位数从 389.3 ms 降至 111.8 ms（降低约 71%），VS Code 从 412.8 ms 降至 140.7 ms（降低约 66%）。已准备页面分别为 111.8 / 191.1 ms、125.6 / 196.3 ms（中位数 / P95），均因中位数超过 100 ms 而未同时达到两项目标。VS Code 首次遍历仍有较长等待，不能用重复遍历成绩代替。

Firefox 与 WebKit 的 CPU 转场实际像素从 128 × 80 恢复到 1600 × 1000，像素数增加 156.25 倍；开始响应中位数分别由 1657.5 → 4583.0 ms、369.5 → 753.0 ms。Firefox 第 4 页 `InvertedPageCurl` 的 10 次样本中，开始响应中位数 13642.5 ms，转场执行中位数 13362.0 ms。两种 CPU 环境的六页均驻留、50 次入口画面全部命中，仍然很慢，说明缓存复用并没有消除完整分辨率着色器的执行成本。这里也观察到后台排队时间，尚不能宣称前台等待已经消失。

局部 `.lay` 修改的 32 个环境／场景组合中，**0 个同时满足中位数 ≤100 ms、P95 ≤200 ms**。浏览器中位数范围为 Chromium 144.6～210.7 ms、Firefox 412～679 ms、WebKit 125～189 ms；VS Code 为 144～199.5 ms。复用检查通过，端到端实时目标仍未达到。

VS Code 的共享 LCSS 标题／曲线改色，当前页中位数为 185.0／396.5 ms，整份放映同步为 2294.0／2534.5 ms；记录中使用六个编译 Worker，没有固定四 Worker 截断，但整份同步仍明显偏慢。laydoc 改名、重排、新增、删除的整份同步中位数约 191～192 ms。当前成果不能宣称已经彻底解决整份放映准备的等待。

## 验证范围与证据解释

核心会话测试覆盖控制流、闭包、递归、增量循环、共享模块、资源及字体恢复、错误与取消恢复、160 次连续修改及撤销、会话关闭释放。依赖图测试保留六页各 5,000 个子记录，验证父计算重放后子记录仍存活，替换与删页后释放。

三种浏览器的逐次求值检查均确认：第 6 页局部文字／颜色／位置变化和 LCSS 标题改色，曲线路径构造与几何重建均为零；LCSS 全部曲线改色更新 1,536 个外观节点，仍为零次曲线路径构造、零次几何重建。尺寸变化只允许对应矩形的一次几何重建。这里统计所有求值尝试，包含中途让出后的续算，证据保留在 `reuse/verification.json`。

真实文字容量测试保留 158 页、16,848,950 字节的排版缓存估计值，超过旧 16 MiB 上限；逐页改色的排版重建为零，删除页面后缓存归零。原生 Skia 另实际分配并读取 10,001 × 10,000 的画面（RGBA 400,040,000 字节），确认预览不再被一亿像素门槛拒绝。

资源阈值测试实际分配 130 项、共 260 MiB 的 Uint8Array 缓冲区，检查未变化补丁零次重新读取／解码，资源删除后释放。这个单元测试的 GPU 图片句柄为模拟对象；12 页各 257 MiB 的页面保留测试使用逻辑成本值，并未分配 3 GiB 显存。它们用于验证淘汰决策与引用生命周期，不是进程 RSS 或物理显存测量。

浏览器回归另外核对实际 CanvasKit 缓存画面、全分辨率转场、页面边界、超过八种效果保留和 4K 图层缓存；转场着色器兼容测试覆盖 125 种效果。六页静态绘图与每页三个动画时刻对照上一版，保存重开和播放版导出在离线网络拦截下验证。冷启动编辑、连续输入、中文组合输入、语法错误及恢复使用独立回归。

“存活派生缓存估计”与“WASM 保留容量”分开报告。WASM 已扩大的线性内存未必归还操作系统，不能把它解释为仍引用所有历史对象；同样，有限时长的稳定记录不等于证明任意文档永远没有内存增长。

静态纹理回归曾出现一次失败：测试使用固定等待后读取一帧的缓存计数，未明确确认该帧已绘制。复现中纹理保留正确；测试改为等待实际 GPU 完成，并拒绝把跳过帧作为缓存样本后通过。原失败日志保留于 `evidence/static-cache-initial-failure.log`，产品包未因这项测试修正而变化。

## 复跑

构建入口沿用 `scripts/build-web-export.py`、`scripts/refresh-web-runtime.mjs`、`scripts/prepare-web-preview-state.mjs`、`scripts/build-editors.py` 和 `scripts/package-editor.py`。运行时、原生编译器、HTML 和 VSIX 应从同一工作区版本生成。原附件作为输入，新文件使用独立输出路径。

在仓库根目录使用 `.venv/bin/python scripts/benchmark-resource-lifecycle.py`，传入以下参数：

```text
--html 新HTML路径
--baseline navigation-preview-v004的HTML路径
--binary target/lifecycle-v005-extension/bin/laymesh
--extension target/lifecycle-v005-extension
--baseline-extension target/navigation-v004-extension
--fixture target/property-preview-fixture
--output 新测量目录
--phase validation
--site-url http://TAILSCALE_IP:18768/
```

先运行 `python3 scripts/serve-preview.py --bind TAILSCALE_IP --port 18768 --directory site/dist`，使用 Tailscale 地址，不使用公网监听。环境需提供 Playwright 及三种浏览器，必要时设置 `PLAYWRIGHT_MODULE` 和 `NODE_PATH`。验证通过后将 `--phase` 改为 `timing`，同机顺序执行；`--resume` 仅复用相同命令的已通过阶段，不能跨构建版本复用。

主要脚本：`test-presentation-keyboard.cjs`、`test-vscode-keyboard.py`、`test-web-semantic-performance.cjs`、`test-web-document-performance.cjs`、`test-vscode-semantic-performance.py`、`test-vscode-document-performance.py`。测试状态、命令、耗时与原始记录位于本报告同名数据目录。
