# 首次编辑、并行编译与逐页放映修复

## 修复内容

v008 更新了 WASM 编译器，却保留了旧编译器的 `preview-state.json`。严格校验因此拒绝整个依赖索引，首次局部修改使六页失效；旧放映入口又等待全部页面编译完成。这是交付回归。

运行时刷新工具现在用即将装入附件的编译器、作品源码、字体和绑定重新求得每页依赖，再生成完整校验索引。索引作为派生缓存更新，作品的 31 个非运行时条目逐字节保留。普通导出、浏览器保存和运行时刷新沿用同一索引格式及严格的加载校验；缺失或失配的旧索引仍保守验证，不替换哈希绕过检查。

离线编译改为文档持有的常驻 Worker 池。当前页先提交，再按待处理页面和浏览器可用并行度启动其他 Worker；页面保持归属，复用语义会话、字体及绘图基线。后续请求发送文件和资源差量。结果经过单一提交队列合并，过期结果不能覆盖当前版本；删除页面和关闭文档释放相应 Worker 与记录。

放映在目录和起始页就绪后开播，其他页继续编译和准备。进入尚未就绪的页面会提高其优先级，保留当前画面；后续页错误不阻止已就绪页播放。单页等待不再等待无关任务，缺失页面会报错。等待和页面数据均绑定源码版本；保存及导出仍要求全部最新页面成功。

首次编辑自动记录初始化、排队、目录、每次语义求值与中断重试、绘图、序列化、提交、当前页显示和整稿完成。失败及取消的计算也计入诊断总量。保留首次和当前编辑记录，不累计历史补丁作为存活内存。没有打开文件时预编译全稿，也没有降低路径或显示精度。

## 验证期间另发现的 WebKit 问题

新增编译并行与放映同时运行时，默认 WebKit 的部分 Worker 曾出现超过 180 秒的等待。单独编译约 2.7 秒；暂停预加载、取消时间片、改标量 WASM 均未消除同时放映时的异常。仅在隔离诊断进程提高 `JSC_maxNumWasmFastMemories` 后，同样操作约 3.5 秒完成。这是定位用对照，交付物和正式测试没有使用该选项。

[WebKit 的内存实现](https://github.com/WebKit/WebKit/blob/main/Source/JavaScriptCore/wasm/WasmMemory.cpp)显示，快速内存不可用时，普通内存每次扩展会重新分配并复制已有堆。[默认策略](https://github.com/WebKit/WebKit/blob/main/Source/JavaScriptCore/runtime/OptionsList.h)限制进程内的快速内存实例数。多个编译及渲染实例共同触发该回退，叠加 Rust 分配器细粒度扩展，产生大量重复复制。

修复保持 dlmalloc 的对象分配和释放，改为按需求成倍扩展线性内存，并将整块新空间交给分配器复用；较大的扩展无法分配时重试本次最小需求。没有容量或 Worker 数量配额。释放的块由分配器复用；WASM 线性内存通常不收缩，文档关闭、Worker 销毁后释放实例。其高水位占用和活跃场景缓存分开统计。默认 WebKit 候选复测约 4.2 秒完成，正式数据以下述最终附件为准。

另移除了冷解析时没有旧节点可匹配却仍生成语法结构指纹的工作，保留后续编辑的节点身份匹配。单独这项优化并未消除上述 WebKit 异常。

**这不是用户那次 Chrome／Edge 接近一分钟等待的完整解释。** 用户环境尚无对应阶段记录，不能将 WebKit 诊断结果套用到那次录屏。

## 测量方法

正式测量串行进行，不与构建或其他浏览器任务并发。浏览器直接从 `file://` 打开最终独立 HTML，阻断外网请求。编辑计量视口为 1600×1000。Chromium 每种修改使用 50 个新隔离上下文；每次第一次修改为冷样本，紧接着第二次修改为暖样本，共 300 次编辑。这里的“冷”指新文档会话和未进行源码编译，不代表清空操作系统磁盘缓存或浏览器机器码缓存。

- `.lay`：修改封面颜色，必须只编译封面，其他五页结果对象保持复用。
- LCSS：追加确实影响全部六页的共享颜色及边框色，检查六页实际输出，并验证多个编译 Worker 执行区间重叠。
- `.laydoc`：保持封面为起始页，重排其他五页，随后恢复原顺序；检查目录顺序。

通过编辑器真实变更事务提交源码，保留 30 ms 输入合并窗口，随后立即请求窗口放映。分别记录输入结束至当前页提交显示、至起始页可播放、至整稿最新版本完成。全稿耗时包含实际后台编译与并发放映，不能用提前开播时间代替。首次和暖更新分开统计，中位数与最近秩 P95 由原始样本计算。

诊断中 v005/v008 的单次无预热对照保留在 `diagnostics/initial-v005-v008.json`，只作为回归定位证据，不与正式 50 样本结果混合统计。

## 用户环境诊断

若仍遇到长等待，复现后在 Chrome／Edge 开发者工具控制台运行验证包中的 `collect-first-edit-diagnostics.js`，会下载 `laymesh-first-edit-diagnostics.json`。无需在首次修改前打开开发者工具；运行时已自动记录首个编辑过程。记录含版本、页面、阶段耗时、重试及当前 WASM 占用，不包含作品源码和字体文件。

## 正确性与回归范围

最终附件在 Chromium、Firefox、WebKit 均通过以下检查：

- 阻塞无关页编译时，起始页可以开播；等待一个已提交页面无需等待整稿。
- 后续页语法错误、请求错误页、修正后恢复、版本取消、准备中关闭以及重新开播。
- 首次连续 20 次改色最终显示最新颜色，编译目标始终只有封面，其他五页结果对象保持复用。
- 六页规范化场景与 v008 一致；每页 0 / 3 / 6.5 秒的画面哈希一致，共每浏览器 18 个采样点。
- 源码仍在等待编译时保存，重开后六页依赖索引全部恢复；再导出播放版并离线打开。测试没有外网请求及页面异常。

调度、依赖索引、输入合并、中文输入法组合状态、稳定 Worker 归属、差量传输、版本等待、单一提交队列、已删除页、初始化失败恢复和生命周期均有契约测试。中文输入法契约测试覆盖组合状态下的暂停/恢复，未声称在本机操作了特定操作系统输入法。Rust 会话单元测试 4 项、完整语义序列测试 29 项通过；分配器额外验证了对齐、扩容数据保留、零初始化、引擎内存约束下的最小扩展回退，以及释放后 20 轮重复分配不继续增长。

动画性能另使用真实方向键自然播放六页两遍，不跳过动画或修改作品时长。帧间隔按成功绘制回复计，跳过的提交包含在下一次成功回复间隔中；它不是显示器扫描输出，也不等同于实机 60 fps。VS Code 使用隔离配置、原生编译服务及实际 Webview 资源链路；现有原生编译调度保持不变。
