# 全分辨率预览与 PDF 压缩验证（2026-10-05）

本次按最终要求直接显示完整分辨率素材，取消代理、空闲升级、逐图双缓冲与 JPEG/PNG 候选体积比较。VS Code 预览的不透明素材采用 JPEG 90，16 位素材转为 8 位显示；实际含非完全不透明 Alpha 的素材采用 WebP 有损模式，默认质量 90、method 0、alpha_quality 100。PDF 使用独立的源像素处理链路，默认保留透明度和 16 位精度，不嵌入 WebP。CLI、Python/Jupyter 和 VS Code 默认导出 DPI 为 1200，layout_dpi 保持独立。

## 同机性能测量

使用真正的 VS Code 扩展宿主与 webview，1440 × 1000 视口、DPR 2、Linux x64、无 GPU 的 Electron 测试。测试源为 `video/04-demos/main-figure/figure.lay`，包含三张 1536 × 1024 RGB PNG、绘图、标注和公式；测量从原生请求入队到图片解码完成并可见，排除编辑防抖。先生成首屏，再进行一次预热文字修改及五次测量。对照使用改造前的原生引擎及内嵌 SVG 兼容路径，其他测试环境相同。

| 指标 | 改造前 | 当前实现 |
| --- | --- | --- |
| 首屏可见耗时 | 2262 ms | 486 ms |
| 五次文字热刷新 | 1966, 1953, 1856, 1972, 1968 ms | 732, 874, 546, 104, 529 ms |
| 热刷新中位耗时 | 1966 ms | 546 ms |
| 每次热刷新 JSON 响应 | 17,644,470 字节 | 81,203 字节 |
| 热刷新新增资源 | 重传内嵌图像与字体 | 0 |

热刷新中位耗时降低 72.2%，达到至少 50% 的目标。当前首屏还需加载图片 2,093,278 字节、字体 1,150,016 字节；响应体积不代表首屏总传输量。图片节点、解码结果和字体规则在文字修改时复用。结果适用于本机此示例，并非所有设备或文档的速度保证。最终方案取消空闲预加载，因此预加载开启/关闭的性能比较不再适用。

## 功能与回归验证

- PDF 检查 `/DCTDecode`、无损 Flate、`/BitsPerComponent 16`、透明软蒙版，覆盖照片、线图、灰度单通道 JPEG、透明与 16 位素材、强制 JPEG、关闭精度/透明度保留及背景合成；检查 JPEG 原始字节直嵌和强制重编码。不同来源即使规范化像素相同，也必须匹配原始 JPEG 内容哈希后才能直嵌。
- 按物理尺寸与组缩放检查降采样；关闭降采样时保留源尺寸。示例实际 PDF 的三张图均为 JPEG、1536 × 1024、8 位 RGB，源分辨率约 488 DPI，未因 1200 DPI 上限而放大。公式和文字保持矢量。
- 复用 ICC、CMYK/YCCK、方向、裁剪、透明度、16 位 TIFF/PNG、字体及公式回归检查；小图片采样不放大，避免把重复插值像素误判成线图。
- 验证全局、项目、显式配置与单次参数优先级；VS Code 用户/工作区值只使用显式设置。参数修改、项目配置创建/删除及磁盘素材修改会刷新；精确文件异步轮询为系统监视器耗尽或配置目录不存在提供回退。
- Python、CLI、Jupyter 的导出格式、1200 DPI 默认、PDF 覆盖参数、像素上限与失败后保留旧输出通过验证。重复图片实例共用资源，低缓存预算保持当前必要工作集，超预算单图编码独占并行处理资源。
- 真正的 VS Code 截图检查：普通 JPEG 像素为 `[29,150,219,255]`，半透明 WebP 在白底上为 `[255,127,127,255]`，16 位灰度经 JPEG 显示为 `[136,136,136,255]`。缩放、平移、标尺、坐标、语言/主题切换、连续编辑、旧结果丢弃、错误恢复、进程重启和关闭/重开均通过，无浏览器异常。

运行的检查包括 `image_policy`、`export_formats`、`legacy_exports`、`image_color_contracts`、`image_formats`、CLI `preview`/`legacy_cli`，Python `test_export_formats`/`test_ipython`/`test_bridge`，以及 `cargo check -p laymesh-wasm`、Node 语法检查。原生 release 引擎与 VS Code 本地包二进制匹配，VSIX 完整性、平台、翻译与许可证检查通过。本次未发布 Marketplace 或 PyPI，未安装到用户的 VS Code。

## 后续热点修复：字体索引与 100 ms 防抖（2026-10-05）

字体名称和 PostScript 名称改为延迟建立索引，保持字体目录顺序、规范化别名及原有匹配规则，注册新字体时失效。预览在单次编译内复用成功加载的图片，避免校验、布局和重复实例重新读取并哈希同一路径；下一次编译重新读取，失败不缓存。VS Code 默认防抖由 250 ms 改为 100 ms，显式用户设置仍优先。

使用同一 Linux 虚拟桌面、1600 × 1000 正常 X11 VS Code 窗口和 60 fps 录屏复测，全程未连接调试接口。仅将三图示例的标题换成 A/B 字符以识别变化帧；简单示例只有文字和矩形。热刷新从源码文字在录屏中变化到预览文字变化，各六次，包含防抖。

| 场景 | 修复前热刷新中位数（250 ms 防抖） | 修复后热刷新中位数（100 ms 防抖） | 修复后六次耗时 |
| --- | --- | --- | --- |
| 三图、绘图及文字 | 334 ms | 133 ms | 133, 133, 133, 133, 150, 116 ms |
| 无图片的简单布局 | 266 ms | 117 ms | 100, 100, 134, 117, 134, 117 ms |

录屏量化精度约 17–33 ms，虚拟桌面结果不代表物理显示器或键盘到屏幕的延迟。冷预览仅各一次，从打开预览命令到完整画面：三图约 320 ms、简单布局约 187 ms，不含 VS Code 启动；单次记录不足以判断冷启动改善或回退。原有无头测试在运行中连接调试器会改变动画帧等待，因此不应与这组无调试接口录屏直接比较。

独立原生进程预热后 20 次请求的往返中位数约 20.8 ms。修复前后 22 帧的 SVG 与检查数据共 44 项全部一致。字体、图片格式/色彩、预览协议、PDF/预览图片策略回归以及 WASM crate 编译检查通过。本地 Linux VSIX 已重建并通过完整性、二进制一致性和平台检查；未发布或自动安装。

### 跨刷新图片内容哈希复用

在上述修复之后，预览增加有界的原始文件字节缓存。每次仍读取文件并逐字节比较；完全一致时复用内容哈希，变化、首次读取或缓存未命中时计算 SHA-256。缓存上限为总缓存预算的 1/8、最多 32 MiB 与 128 个路径，并计入原有总预算，不仅依赖文件大小或修改时间判断变化。100 ms 默认防抖保持不变。

同机原生请求往返采用修复前、修复后、修复后、修复前的顺序，各预热两次后测量 30 次：中位耗时分别为 20.71、17.47、16.80、21.32 ms。这里不包含防抖、webview 或显示等待，未将约 4 ms 的原生收益宣称为录屏总耗时改善。四轮共 176 项 SVG/检查数据比较全部一致；等长且恢复原修改时间的素材替换、删除与恢复均通过验证。字体资源等其他哈希不属于此次缓存范围。

## 字体回退候选排序缓存与防抖设置入口（2026-10-05）

按字重和斜体缓存系统回退候选顺序，新注册字体时失效；字形覆盖、嵌入限制和当前位置警告仍实时检查。显式字体列表仍禁止使用未列出的字体。

同机 ABBA 顺序、每组 30 次热刷新，原生请求往返中位数从 16.80/16.87 ms 降到 14.74/15.32 ms。插桩 release 的候选构造累计耗时从上一轮 3.044 ms 降到 0.629 ms，编译从 14.439 ms 降到 12.069 ms（嵌套计时不能直接相加）。176 次 SVG/inspection 比对一致；53 项核心单元测试与 5 项字体渲染契约通过。

新增命令“LayMesh：设置预览防抖时间”，可输入 0–5000 的整数毫秒值，默认 100，0 关闭防抖；保存到工作区或无工作区时的用户设置，立即生效。命令输入校验、取消操作和保存范围已验证。调试器提前连接的 30 次 VS Code 热刷新原始记录保存在本轮 preview-candidate-cache 产物中；口径为资源就绪后的动画帧确认，不是物理屏幕呈现时间。
